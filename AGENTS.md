# Repository instructions

Read [`AGENT-WORKING-AGREEMENTS.md`](AGENT-WORKING-AGREEMENTS.md), then
[`profiles/sansfaux.md`](profiles/sansfaux.md), on the trigger the core's
opening paragraph sets: before your first delivery, dispatch, write or GitHub
action in this repository; a read-only look needs no read. This file adds
only what is specific to this repository; it never overrides Parts A–B, and a
rule here that contradicts one there is the rule that is wrong.

## Commit subjects

Commit subjects you write use `type(scope): description`. Append `(#issue)`
when the change has an issue; otherwise, omit the suffix rather than inventing
one. Subjects generated by Git or GitHub are left as generated.

This convention is local to `brandonperfetti/agent-working-agreements`. Do not
apply it to another repository unless that repository records the same rule in
its own instructions.

## Amending the agreement

The agreement stays small on purpose; these rules are what keep it small.

- **A rule earns its place after something bit and Brandon agreed it bit.** An agent that
  meets a rule's cost records friction (A6) and opens no amendment in that session. Brandon
  decides which friction becomes a rule, and batches the amendments: one agreement PR at a
  time.
- **An amendment replaces or shortens; it layers nothing on top.** The core, each profile and
  each client file do not grow net lines; studio-specific text goes to the profile, never the
  portable core. Procedure goes to `procedures/` (read when its trigger occurs;
  four fields on top, indexed in two places) or the skill that owns it; the agreement keeps the
  invariant and a pointer. A rule moves only once its destination carries it, is linked from
  where it stood, and has been reviewed.
- **Evidence lives in `_agent/`, not in the rule.** No line numbers, hashes or captures of
  mutable files in the agreement or an appendix; a rule cites a learning or an issue.
- **Positive phrasing.** Say what to do; a prohibition is for a hard boundary only.
- **The changelog entry is short:** what changed, why, who decided, one receipt link (issue
  numbers in the heading are identifiers, not receipts). Under ten lines.
- **Stable anchors.** A1–A8, B0–B2 and the client file names stay; shrink their bodies, never
  rename them.

## CI gate

Green is these six commands, run in this order from the repository root, each
exiting 0:

```bash
./scripts/check-index.sh
./scripts/check-index.test.sh
./scripts/check-structure.sh
./scripts/check-structure.test.sh
/usr/bin/python3 -m unittest discover -s hooks/claude-code
npx --yes markdownlint-cli2
```

`check-structure.sh` holds the core plus each profile, and each client file,
under their line ceilings, keeps studio-specific text out of the core, requires
every file under `procedures/` but `README.md` to carry its four fields and be
a row of `procedures/README.md`'s table and a profile's *Triggers* table (or, for
`procedures/<client>/`, linked from that client's appendix), and rejects a 40- or
64-hex pin in normative text; `history/` is exempt from the pin rule.
The `unittest` run tests the Claude Code hooks under `hooks/claude-code/` and their
installer.
`check-index.sh` proves the composition: every client a row of a profile's
*Client adapters* table, every root and client opener naming core and profile (a
client's also its own file), the core naming no profile, the anchors present.

No environment export is needed. They are the steps of the job `check` in
`.github/workflows/check.yml`, and `check` is the required status check on
`master`. `markdownlint-cli2` lints the files its config's `globs` name
(`.markdownlint-cli2.jsonc`), symlinks included. CI runs it through
`DavidAnson/markdownlint-cli2-action`, which carries its own copy, so a local
`npx` may resolve to a different version from CI's.
