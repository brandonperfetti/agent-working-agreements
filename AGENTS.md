## Commit subjects

Commit subjects you write use `type(scope): description`. Append `(#issue)`
when the change has an issue; otherwise, omit the suffix rather than inventing
one. Subjects generated by Git or GitHub are left as generated.

This convention is local to `brandonperfetti/agent-working-agreements`. Do not
apply it to another repository unless that repository records the same rule in
its own instructions.

## Amending the agreement

The agreement stays small on purpose; these rules are what keep it small.

- **A rule earns its place after something bit and Brandon agreed it bit.** An agent that
  meets a rule's cost records friction (A6) and opens no amendment in that session. Brandon
  decides which friction becomes a rule, and batches the amendments: one agreement PR at a
  time.
- **An amendment replaces or shortens; it layers nothing on top.** The core, each profile and
  each client file do not grow net lines; studio-specific text goes to the profile, never the
  portable core. Procedure goes to `procedures/` (read when its trigger occurs;
  four fields on top, indexed in two places) or the skill that owns it; the agreement keeps the
  invariant and a pointer. A rule moves only once its destination carries it, is linked from
  where it stood, and has been reviewed.
- **Evidence lives in `_agent/`, not in the rule.** No line numbers, hashes or captures of
  mutable files in the agreement or an appendix; a rule cites a learning or an issue.
- **Positive phrasing.** Say what to do; a prohibition is for a hard boundary only.
- **The changelog entry is short:** what changed, why, who decided, one receipt link (issue
  numbers in the heading are identifiers, not receipts). Under ten lines.
- **Stable anchors.** A1–A8, B0–B2 and the client file names stay; shrink their bodies, never
  rename them.

## Release tags

Rules here take effect at release, so every release carries a tag. The tag names what has been
in force since, and it is the version a rollback returns to.

- **After Brandon merges a release PR into `master`, the orchestrator tags that merge commit and
  pushes the tag**, without asking again (Brandon, 2026-11-17). This is ritual step 7 for this
  repository only. In every other repository Brandon tags, and an agent tags only on his explicit
  words for that one tag. A pushed tag stays as it is; moving or deleting one is Brandon's.
- **Name:** `vYYYY.MM.DD`, the date of the merge. A later release on the same day adds `.1`, then
  `.2`.
- **Annotated, under RULE ZERO.** The message says in plain words what the release puts in force
  and closes with one `Agent:` line. The tagger email is Brandon's. Fetch, then name the merge
  commit: `git tag -a <tag> <merge commit>`. The guard reads the commits a push sends, not the tag
  itself, so read the tag back (`git cat-file -p <tag>`) for its object, tagger and message before
  pushing it.
- **Create the tag in one call and push it in the next:** `git push origin <tag>`, alone. The
  guard reads a push before the command runs; a tag made in the same call does not exist yet, so
  that push is refused as unreadable.
- **Then carry `master` home to `develop`** (ritual step 8; no workflow does it here). Once the
  tag is pushed, the orchestrator fetches, then merges `origin/master` into a `develop` that is
  at `origin/develop`, with a merge commit (`git merge --no-ff origin/master`, under RULE ZERO),
  and pushes it to `develop`, without asking again (Brandon, 2026-11-17). Before the push it
  confirms that the merge changes no file: `git diff origin/develop HEAD` prints nothing. If the
  merge conflicts or would change a file, stop and ask Brandon: something reached `master` that
  `develop` does not have. This is the one push to `develop` the rule covers.
- **That is the whole release:** no GitHub Release page, no version file, no package.

**Rollback** is Brandon's decision. In `~/dev/sansfaux/agent-working-agreements`, check the tag
out and re-run the installers that version carries; each one's `--check` then says whether the
installed guard matches it. A tag older than an installer leaves that hook as it was: skip its
line. Start a new session afterwards, and for OpenClaw run its canary
([`hooks/openclaw`](hooks/openclaw/README.md)). That checkout is OpenClaw's protected root, so it
is off `master` until Brandon ends the rollback.

```bash
git checkout <tag>
/usr/bin/python3 hooks/claude-code/install.py
/usr/bin/python3 hooks/codex/install.py
node hooks/openclaw/install.mjs
```

## CI gate

Green is these nine commands, run in this order from the repository root, each
exiting 0:

```bash
./scripts/check-index.sh
./scripts/check-index.test.sh
./scripts/check-structure.sh
./scripts/check-structure.test.sh
/usr/bin/python3 -m unittest discover -s hooks/claude-code
/usr/bin/python3 -m unittest discover -s hooks/codex
node --test hooks/openclaw/relay.test.mjs
./scripts/openclaw/runbook.test.sh
npx --yes markdownlint-cli2
```

`check-structure.sh` holds the core plus each profile, and each client file,
under their line ceilings, keeps studio-specific text out of the core, requires
every file under `procedures/` but `README.md` to carry its four fields and be
a row of `procedures/README.md`'s table and a profile's *Triggers* table (or, for
`procedures/<client>/`, linked from that client's appendix), and rejects a 40- or
64-hex pin in normative text; `history/` is exempt from the pin rule.
The first `unittest` run tests the Claude Code hooks under `hooks/claude-code/` and their
installer; the second tests the Codex hook under `hooks/codex/`, which hands Codex shell
commands to that guard, and its installer; `node --test` tests the OpenClaw relay under
`hooks/openclaw/`, which hands OpenClaw tool calls to that guard. `runbook.test.sh` drives
`scripts/openclaw/runbook.sh` through the stop and retention branches of
`procedures/openclaw/managed-worktrees.md`, on disposable repositories and a stub
`openclaw`; it never reaches a live checkout or Gateway.
`check-index.sh` proves the composition: every client a row of a profile's
*Client adapters* table, every root and client opener naming core and profile (a
client's also its own file), the core naming no profile, the anchors present.

No environment export is needed. They are the steps of the job `check` in
`.github/workflows/check.yml`, and `check` is the required status check on
`master`. `markdownlint-cli2` lints the files its config's `globs` name
(`.markdownlint-cli2.jsonc`), symlinks included. CI runs it through
`DavidAnson/markdownlint-cli2-action`, which carries its own copy, so a local
`npx` may resolve to a different version from CI's.
